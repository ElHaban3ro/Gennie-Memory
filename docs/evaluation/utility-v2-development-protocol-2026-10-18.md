# Protocolo previo: utilidad v2 con compatibilidad de referente

Fecha: 2026-10-18. Variante nueva explícita `utility_v2`, motivada por las tres selecciones de otro referente de `utility_v1`. Se conserva la política antigua para reproducirla y la base sigue predeterminada. El cambio es una instrucción de elección, no un filtro determinista ni una garantía de aplicabilidad: pide comprobar primero sujeto, edición, sede, equipo, entorno, tiempo y condiciones especificados, y prohíbe transferir valores entre referentes o completar las partes desconocidas con datos de otro contexto. Acepta una corrección explícita del sujeto solicitado sin tratar la negación de la premisa como incompatibilidad. Después admite respuesta, corrección o parte concreta útil. La descripción de `none` es exactamente la de `utility_v1`; no se añade gate, segunda llamada, regex, modelo o estado persistente.

Primera prueba: los 64 casos de `conversation-evidence-v2`, con 224 recuerdos. **Son desarrollo conocido y fueron usados para formular la hipótesis.** No se presenta su revisión ciega anterior como una validación intacta de esta nueva instrucción. No se cambian fuente, pregunta, etiqueta, revisión o justificación, y el prompt no incluye IDs, ejemplos ni respuestas del banco.

Antes de llamar se congelan protocolo, instrucciones, casos derivados y hashes del código/binarios. Se usa Decisions, `keywords`, límite 20, una SQLite temporal y un único proceso `session`. Se ejecutan 128 operaciones, ambas políticas adyacentes por pregunta y orden alternado por posición original. `prepare-utility-comparison <banco> <salida> utility_v2` conserva etiquetas; `campaign ... 128 per_case` transmite solo búsqueda y política. Duración prevista: 1–2 minutos; registrar tokens y gasto informado, modelos y recibos faltantes. No se reintenta un resultado incierto ni se ejecutan variantes sucesivas para rescatar el resultado.

Bloqueos previos: perder cualquier evidencia útil seleccionada por la base del mismo par, seleccionar cualquier ID no permitido (incluida ausencia) o introducir degradación nueva. Se exige además al menos una evidencia útil adicional para pasar a otra validación. Se informan las cuatro relaciones separadas, diferencias por caso y el estado de los tres fallos conocidos. La comparación principal es con la base nueva emparejada; cualquier referencia a `utility_v1` o a la base anterior es histórica, no una comparación simultánea de tres políticas.

Antes de interpretar se auditan hashes, eventos, fuente declarada, texto, ámbito, revisión, estado y vigencia de semillas y candidatos. Las listas de candidatos deben ser idénticas. El reporte permite reproducir las preparaciones históricas de `utility_v1` cuando no consta `candidate_policy`; con v2 registra esa identidad de forma explícita para evitar confundir políticas. Las gráficas identifican la variante y los tokens como entrada a Decisions, no a Codex.

El resultado puede descartar o mantener la hipótesis en desarrollo. Incluso pasar no cambia el predeterminado ni demuestra generalización: antes de promover hace falta otra cohorte preparada bajo el prompt congelado y con anotación separada previa a resultados; siguen pendientes preguntas humanas, fuentes externas, respuesta final e integración. No se relabela este banco ni se lo reutiliza como reserva. El README y las campañas históricas permanecen identificados por su ruta y cohorte.
