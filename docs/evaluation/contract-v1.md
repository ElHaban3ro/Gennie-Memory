# Contrato de evaluación v1

Estado: banco sintético generado y validado; campañas locales y remotas de desarrollo ejecutadas con composición de semillas. La evaluación final y el contrato completo de producto siguen pendientes. Fuente de requisitos: [ROADMAP.md](../../ROADMAP.md) y [README.md](../../README.md).

## Corpus y etiquetas

`scripts/generate_benchmark.py` produce `tests/benchmark/v1/` de manera determinista. La versión actual contiene 400 entidades ficticias, 840 memorias distintas, 880 revisiones y 10.800 consultas: 10.000 positivas con 25 formas de preguntar por entidad y 800 negativas. Cada consulta fija ámbito simulado, instante UTC, IDs relevantes, hecho esperado, IDs prohibidos, segmento y origen de la etiqueta. Las particiones desarrollo, calibración y final se asignan por entidad para que sus paráfrasis no crucen conjuntos. `scripts/validate_benchmark.py` verifica hashes, unicidad, particiones, ámbito, vigencia y correspondencia entre hechos y memoria actual.

El corpus ejercita español, inglés, alias, ausencia de entidad, ámbito no asignado, distractores de otro ámbito, revisiones corregidas y recuerdos caducados. La procedencia de las etiquetas es una regla determinista del generador; **todavía falta revisión humana de una muestra**. Los 25 patrones no equivalen a miles de maneras lingüísticas independientes: la cifra grande mide variaciones por entidad y no se presentará como diversidad humana demostrada. Faltan condiciones complejas, contradicciones entre fuentes, sensibilidad y textos largos para cubrir el diseño completo.

La [versión 2](../../tests/benchmark/v2/manifest.json) corrige una fuga de respuesta de v1: cada tipo de tarea tenía siempre la misma preferencia. Ahora hay seis valores ficticios por tipo, repartidos de forma determinista por entidad. Contiene 400 entidades, 840 memorias, 880 revisiones y 41.600 consultas: 40.000 positivas, 1.600 negativas. `forms.json` enumera 1.000 formulaciones componibles a partir de 20 marcos de intención, 10 prefacios y 5 cierres; cada entidad recibe 100 formas repartidas entre los 20 marcos. Incluye alias, inglés, mezcla de idiomas, contexto distractor, tarea equivocada y una instrucción explícita de no consultar recuerdos. Son **1.000 formas superficiales auditables**, no 1.000 intenciones humanas independientes. Aún faltan condiciones, fuentes inciertas y revisión humana de etiquetas. La partición final de v2 permanece reservada.

`scripts/select_benchmark_cases.py` extrae una muestra equilibrada y determinista de una partición para pilotos. El archivo de 50 casos de desarrollo usado en el segundo piloto se eligió antes de inferir con Laya; su SHA-256 se registra en [pilotos](pilot-2026-10-15.md). La selección de cuatro casos remotos de ese piloto sí se hizo después de ver errores de Laya y no sirve para estimar superioridad entre proveedores.

La opción `--cover-forms` del selector v5 escoge una consulta positiva por cada forma declarada y `--per-segment` controles negativos por segmento; permite excluir varias muestras previas por IDs y entidades. La muestra de desarrollo de 1.600 casos preparada para la campaña cubre todas las 1.000 formas positivas; el archivo congelado y sus límites constan en [preparación v5](campaign-v5-preparation.md).

La [versión 3](../../tests/benchmark/v3/manifest.json) conserva los mismos textos y etiquetas de v2, y añade `entity_id` a cada memoria y consulta. El identificador lo aporta un **host sintético** a partir del proyecto ficticio; iROMEM todavía no resuelve nombres, alias ni ambigüedades reales. Esto permite una ablación emparejada del filtro estructurado sin atribuirle coste cero a la futura resolución de entidad. Hay una sola memoria activa por entidad y ámbito en este corpus, por lo que v3 mide especialmente la exclusión de otros proyectos; aún falta probar varias memorias y tareas dentro de la misma entidad.

La [versión 4](../../tests/benchmark/v4/manifest.json) cubre esa última brecha: conserva 400 proyectos, 1.000 formas y 41.600 consultas, pero añade dos recuerdos activos de tareas distintas a cada entidad. Sus 40.000 preguntas positivas se reparten entre las tres tareas; la tarea de `wrong_task` sigue sin recuerdo aplicable. Los IDs de memoria son hashes opacos uniformes para que el prefijo del ID no revele cuál corresponde a la etiqueta. El manifiesto incluye 1.680 revisiones y 1.640 memorias únicas. El host aún entrega `entity_id` ya resuelto, las etiquetas siguen siendo deterministas y la revisión humana de una muestra permanece pendiente.

La [versión 5](../../tests/benchmark/v5/manifest.json) añade **aplicabilidad condicionada**: dos recuerdos activos por proyecto para la misma tarea, uno remoto y otro presencial, con valores variados, fuente documental ficticia y condiciones explícitas. Conserva 1.000 formas y produce 42.400 consultas: 40.000 positivas y 2.400 negativas, incluidas preguntas sin modalidad decidida. Hay 1.280 revisiones y 1.200 memorias únicas; 80 revisiones antiguas tienen hechos diferentes y estado corregido. Las etiquetas positivas fijan ID, hecho, condición y referencia de fuente. La fuente es un identificador sintético **declarado**, no verificado frente a un documento real. Las preguntas comparten marcos de v2, por lo que la diversidad lingüística no es independiente de v2–v4. El host sigue proporcionando la entidad. El validador comprueba hashes, particiones por proyecto, ambas modalidades, condiciones, fuentes, hechos y revisiones vigentes; falta revisión humana y más ambigüedad real.

## Entrada, salida y límites

La consulta usa `SearchRequest` (`query`, `scope_kind`, `scope_id`, `entity_id` opcional, `as_of`, `limit`). La línea base Rust aplica ámbito, identidad de entidad cuando se aporta, revisión actual, estado y vigencia antes de limitar candidatos. `search-batch` consume JSONL etiquetado y devuelve una línea por caso con candidatos y latencia de búsqueda. La salida de búsqueda marca `method: fts5` y `semantic_coverage: disabled`; aún no es una semilla. El runner falla si una línea es inválida, sin contabilizarla como acierto.

`compose-seed` recibe exactamente una consulta textual o híbrida, proveedor externo, estado de clasificación, los candidatos `{memory_id, revision}` presentados al clasificador y los seleccionados. Repite el mismo método de búsqueda y rechaza IDs ajenos, duplicados, revisiones obsoletas y elecciones que el clasificador no vio antes de componer texto determinista desde las síntesis guardadas. Si el clasificador falla, devuelve `degraded` sin texto de semilla. `build_seed_requests.py` exige que el informe del clasificador identifique exactamente los candidatos vistos; los informes de pilotos anteriores a este contrato deben regenerarse para usar el puente. `compose-seed-batch` y `evaluate_seeds.py` procesan y miden varias semillas. La migración 4 agrega condiciones y fuente declarada opcionales a la revisión; ambos métodos de búsqueda y la semilla las conservan, y el evaluador v5 mide su fidelidad frente a etiquetas. Esto **no verifica** el documento de origen ni que la condición sea aplicable: eso depende de la selección del clasificador. Falta límite de tokens; no se presenta como el `mem_recall` final.

`session` acepta una línea JSON por operación (`op: search`, `hybrid_search` o `compose_seed`; `request` usa el mismo contrato que la CLI) y responde una línea con estado, tiempo Rust, resultado o error. Conserva una conexión SQLite local durante la ejecución. `scripts/evaluate_pipeline.py` inicia esa CLI; usa Laya cargado una sola vez en Python, top-1 determinista o Jev/OpenAI Decisions por OpenRouter, siempre con etiquetas A/B/C y los mismos candidatos presentados a `compose_seed`. Un fallo del clasificador produce `degraded` y no se contabiliza como abstención correcta. Registra tiempo total por caso, ida y vuelta de búsqueda/composición, decisión, carga/calentamiento local, modelo servido, uso y coste remoto informado. Los percentiles del runner usan interpolación lineal. Exige casos sintéticos etiquetados de desarrollo, condición y fuente en positivos v5; no abre la partición final. El modo remoto exige `--case-id` o un límite de hasta cuatro casos, usa el cliente de sondeo con timeout de 20 s y no reintenta; **no** tiene el diario reanudable de la campaña grande.

El mismo runner acepta `--retrieval hybrid --embedding-batch <lote>` si el lote ya está cargado en la base. Verifica el hash del snapshot SOC y el procedimiento del lote, codifica cada pregunta en vivo con el encoder Laya, llama a `hybrid_search` (filtros + FTS5 + coseno/RRF) y pasa la misma consulta vectorial a `compose_seed`. Mide la generación del vector dentro de cada consulta y separa la indexación, carga y calentamiento. Rechaza preguntas que exceden 512 tokens del encoder. El perfil actual comparte los pesos del clasificador y es experimental, no el perfil independiente previsto en M2.

Para campañas **locales** de desarrollo, `evaluate_pipeline.py --journal <ruta>` sincroniza un registro por caso terminado y permite `--limit` hasta 10.000. El primer registro fija consultas y sus IDs, base SQLite, binario, código del runner, configuración, lote semántico y hashes del modelo Laya cuando aplica. Al reanudar, rechaza entradas distintas, duplicadas o fuera de orden; un caso que falló antes de escribirse se vuelve a ejecutar. Los fallos de decisión registrados permanecen como fallos, no se convierten en aciertos. `--max-seconds-per-run` detiene una invocación antes de iniciar el siguiente caso y conserva lo terminado; un caso individual puede exceder el plazo. El informe se escribe solo al terminar todos los casos. `load_seconds` y `warmup_ms` corresponden a la invocación que escribió el informe; `resumed_cases` revela cuántas filas venían de un proceso anterior. Este diario no se usa con proveedores remotos, pues sus llamadas pueden quedar cobradas con resultado incierto; para ellos rige el diario de `run_openrouter_campaign.py`. La muestra preparada se describe en [campaign-v5-preparation.md](campaign-v5-preparation.md).

Cada fila local conserva `retrieval_snapshot`, los candidatos exactos y ordenados que vio la clasificación, y `retrieval_request`, incluido el vector de pregunta cuando la búsqueda es híbrida. Tras un informe **completo** de desarrollo, `scripts/export_campaign_retrieval.py` valida IDs, etiquetas, estado, conteos, revisiones, IDs prohibidos, espacio vectorial y vector finito; crea un JSONL compatible con `run_openrouter_campaign.py prepare`. `build_seed_requests.py` utiliza el `hybrid_request` congelado de esa exportación para componer y validar una decisión remota; rechaza su ausencia o discrepancia. Un positivo y un negativo sintéticos pasaron el puente de decisiones simuladas a `compose-seed-batch` y `evaluate_seeds` con 2/2 semillas exactas, sin llamar al proveedor. Así Jev y OpenAI Decisions recibieron los mismos candidatos del recorrido local y la semilla se revalidó con el vector usado originalmente.

La primera campaña local v5 completó tres recorridos de 1.600 casos en MPS con cobertura semántica completa y candidatos idénticos. El [informe y los resultados por caso](../../outputs/iromem/evaluation/v5-campaign-development/README.md) están versionados. La exportación de búsqueda produjo un plan remoto de 2.800 llamadas, ejecutado posteriormente con los mismos casos y candidatos; resultados y límites en outputs/iromem/evaluation/v5-campaign-remote/README.md.

Los selectores locales `laya_pairwise`, `laya_pairwise_conditions` y `laya_conditions_choice` son variantes diagnósticas. Las binarias registran puntuación por candidato y usan un umbral indicado por `--threshold`; la variante condicionada añade `conditions` como campo de estado, y la de elección lo añade a la descripción del candidato. No conviertas un barrido sobre desarrollo en calibración ni trates las puntuaciones binarias como probabilidades comparables con el `choice` tipado de OpenRouter.

`select_benchmark_cases.py --exclude-ids <muestra.jsonl>` permite fijar otra muestra equilibrada sin repetir IDs. Compara también `entity_id`: dos muestras de desarrollo sin consultas repetidas pueden compartir proyectos y recuerdos. `--exclude-entities-from <muestra.jsonl>` elimina ese solapamiento de entidad y puede repetirse para varias muestras. El piloto secundario v5 comparte once entidades con el inicial; el tercero excluye las entidades de ambos. Ninguno reemplaza la partición final reservada.

El [paquete v5 de desarrollo](../../outputs/iromem/evaluation/v5-development/README.md) conserva las tres muestras y doce informes integrados por caso con hashes. `python3 scripts/verify_pilot_bundle.py outputs/iromem/evaluation/v5-development` comprueba que los archivos coinciden con el benchmark versionado, que los resultados están emparejados con sus etiquetas y que la tercera muestra no comparte entidades. El paquete no incluye pesos, bases SQLite ni resultados de la partición final.

`scripts/evaluate_retrieval.py` calcula recall@20, top-1, tasa de vacíos para negativos, filtración de IDs prohibidos y percentiles de latencia. Los pilotos `evaluate_semantic.py` y `evaluate_fusion.py` comparan coseno exacto y RRF en **el mismo subconjunto**; el encoder de Laya es una línea experimental, no el perfil de embeddings independiente previsto en M2. `evaluate_laya.py` prueba `choice` y `noul` local con `reason: null`: el modelo no entrega justificación textual. `--choice-labels letters` usa etiquetas cortas A/B/C frente al modelo y restituye los IDs autorizados al informe. Si no hay candidatos, registra `skipped_empty` sin invocar Laya. `scripts/baseline_decisions.py` crea una referencia determinista top-1 sin clasificador que pasa por el mismo puente de composición de semillas. `probe_openrouter_decisions.py` usa el endpoint tipado de OpenRouter con Jev y GPT-6 Luna Decisions, valida IDs y probabilidades y registra uso/coste informado; cuatro llamadas como máximo por invocación y solo casos sintéticos de desarrollo. Los informes registran los IDs presentados.

`export_laya_embeddings.py` puede generar un lote versionado de vectores y la consulta vectorial de un caso sintético, sin modificar la caché de SOC. `load-embeddings` valida y persiste ese lote; `hybrid-search` aplica filtros estructurados, coseno exacto y RRF en Rust, con cobertura explícita. Esto ya permite demostrar la recuperación híbrida de un caso; faltan la campaña completa y sustituir o justificar el perfil de embedding definitivo.
El exportador también genera JSONL de vectores para una partición; `hybrid-search-batch` usa ese archivo y el evaluador exige que todos los casos y etiquetas coincidan. Ya se midió un piloto de 270 consultas de desarrollo, pero no la campaña de 10.800. El índice exacto y la generación de vectores son costes distintos; informa ambos antes de atribuir ahorro de tiempo.

`scripts/run_openrouter_campaign.py` prepara un plan congelado de consultas y candidatos sintéticos, con hashes de ambos archivos, modelos y límites de llamadas, coste reservado y tiempo activo. Exige correspondencia exacta de IDs y etiquetas entre consulta y búsqueda; rechaza IDs prohibidos y duplicados. Su comando `run` escribe y sincroniza en disco un evento `started` **antes** de cada petición y uno `finished` al obtener el resultado. Al reanudar, omite lo terminado; si una petición quedó incierta, se detiene y requiere `resolve-uncertain`, que la cuenta como fallo sin repetirla. `export` solo genera el informe completo compatible con `build_seed_requests.py` cuando todas las tareas tienen estado terminal; `export --partial` conserva resultados obtenidos e indica cuántas tareas faltan o son inciertas. El primer fallo de proveedor detiene el lote para diagnóstico. Los límites de coste y tiempo se comprueban antes de iniciar cada llamada; una llamada puede exceder la reserva o el plazo, por lo que el tope no es una garantía impuesta por OpenRouter. El coste incierto conserva la reserva configurada. Ningún comando de preparación llama a proveedores.

El plan de desarrollo v4 preparado el 2026-10-15 contiene 1.000 consultas equilibradas (100 por segmento), 1.600 llamadas previstas para dos modelos y 200 consultas sin candidatos por modelo resueltas localmente. Hash del subconjunto: `e076aa14c752e6a283412a7ee3cee1d242f7c16798e97f9ba32d8736a0b7358f`; hash del plan: `167dda62b43e8fa4e9583e1aa45dc85e2bdc0b58f04f4937bcd4eecec3d64eec`. El plan local bajo `.local/pilots/` fija máximo de 2.000 llamadas, reserva de US$0,0002 por llamada, límite de US$0,50 y 1.800 segundos activos. **Está preparado, no ejecutado**: los topes y la campaña deben ser aprobados según [testing.md](../rules/testing.md). Las tarifas y modelos se verificarán antes de iniciarla.

Para una comparación final, fijar antes de ejecutarla: tamaño de cada variante, perfil de embedding versionado, candidatos por buscador, presupuesto de llamadas, duración, modelos fijados, umbrales calibrados solo en calibración y política ante rechazo o fallo. La partición final se usará una sola vez con configuración congelada. Deben reportarse precisión y recall por segmento, fidelidad del contenido y condiciones de la semilla, coste, latencia, CPU/RAM, fallos y degradación; las comparaciones entre proveedores requieren el mismo conjunto de casos y presupuesto. El coste de recuperación no demuestra ahorro de tiempo del agente principal sin integración posterior.

## Reproducción de la línea textual

```sh
python3 scripts/validate_benchmark.py tests/benchmark/v1
python3 scripts/generate_benchmark.py --entities 20 --output /tmp/iromem-pilot-v1
python3 scripts/validate_benchmark.py /tmp/iromem-pilot-v1
IROMEM_DATABASE_PATH=/tmp/iromem-pilot.db cargo run --offline -p iromem -- load-fixtures /tmp/iromem-pilot-v1/corpus.json
IROMEM_DATABASE_PATH=/tmp/iromem-pilot.db cargo run --offline -p iromem -- search-batch /tmp/iromem-pilot-v1/queries.jsonl > /tmp/iromem-pilot-results.jsonl
python3 scripts/evaluate_retrieval.py /tmp/iromem-pilot-results.jsonl --queries /tmp/iromem-pilot-v1/queries.jsonl
```

Usa una ruta temporal propia y nueva; `load-fixtures` no está diseñado para recargar la misma revisión en una base ya poblada. Las pruebas del workspace siguen siendo pequeñas; esta campaña no forma parte de `cargo test`.

## Proveedores comprobados el 2026-10-15

- Laya 0.3.5: el snapshot multilingüe de SOC y el intérprete Python configurado por SOC se cargaron en modo lectura. En el proceso restringido `torch.backends.mps.is_available()` devolvió `false`; fuera de él devolvió `true` y los pilotos de rendimiento definitivos para esta etapa corrieron en MPS.
- Jev: [TypeSafe](https://api.typesafe.ai/redoc) publica su API propia; [OpenRouter](https://openrouter.ai/typesafe/jev-1.14) ofrece el modelo en el endpoint de decisiones. Jev 1.14 respondió HTTP 504 en un sondeo; `typesafe/jev-1.13` respondió y quedó fijado para el piloto.
- OpenAI Decisions: la [API de OpenAI](https://developers.openai.com/api/reference/resources/decisions/methods/create) es distinta de la ruta normalizada de [OpenRouter](https://openrouter.ai/openai/gpt-6-luna-decisions-20261006). `openai/gpt-6-luna-decisions` respondió mediante OpenRouter, usando solo `IROMEM_OPENROUTER_API_KEY`.
- Modelo conversacional OpenRouter: pendiente de elección y prueba; no se debe mezclar su JSON generado con probabilidades de decisiones tipadas.

Los precios y la disponibilidad cambian; antes de una campaña se consultará el catálogo actual y se registrará modelo realmente servido, uso y coste por llamada. Ninguna puntuación de un proveedor se interpretará como probabilidad intercambiable con otra sin calibración.
