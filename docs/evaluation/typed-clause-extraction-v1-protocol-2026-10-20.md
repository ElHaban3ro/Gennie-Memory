# Extracción por cláusulas tipadas V1

UTC 2026-10-20. Desarrollo del paso 3, posterior a los pilotos que fallaron [forma y fidelidad](documentary-extraction-openai-results-2026-10-20.md). No se modifica gold, resultados anteriores ni baseline. La etapa anterior fue progreso con resultados negativos, no un pase de calidad.

## Interface y traducción

El módulo puro recibe tipo de tarea, texto, ontología y salida tipada; valida citas y referencias y traduce al DTO documental V5. El parser/resolver V5 permanece como segunda comprobación. El modelo no escribe sus veinte campos genéricos: devuelve cláusulas con cita, referente, contexto, configuración, modalidad y una estructura específica de requisito, propiedad, cantidad, procedimiento, asignación/capacidad/permiso, flujo, disponibilidad documental o conjunto exhaustivo. No se limita todo el recuerdo a un tipo: cada cláusula puede tener otro sujeto/tipo.

Un requisito separa el atributo requerido y si se exige, evitando codificar «no» como objeto o convertir negación en conjunto positivo. Una cantidad conserva un decimal exacto como texto, sin redondeo binario, y separa número, unidad, igualdad/cota y ámbito. Un procedimiento separa magnitud, método y estado; no-realización no genera desconocimiento de cantidad. Capacidad no se traduce como asignación real. La disponibilidad conserva el registro citado, no ignorancia global. Los campos no aplicables no forman parte de cada estructura. Una cláusula inválida degrada toda la fuente; no se ignora para obtener un subconjunto favorable.

El referente separa tipo, nombre, propietarios y cuantificador/cardinalidad, además de pertenencia/componente cuando estén expresos. Los nombres deben estar literalmente en el texto; el tipo es vocabulario de dominio, nunca alias de una entidad del banco. La clave se calcula con una tupla serializada no ambigua, conserva tipo/propietario/componente padre y no consulta frames manuales. No se promete resolver todas las identidades: divergencias de tipado pueden perder coincidencia y colisiones/pertenencias erróneas deben ser revisadas. Cambiar claves no modifica etiquetas ni métricas históricas; las ablaciones manual/auto exponen la incompatibilidad y no la llaman falsedad textual por sí sola.

La fuente declara cláusulas ciertas, lecturas condicionales, exhaustividad y cue literal de incertidumbre. Una lista vacía de lecturas nombradas se traduce a una lectura neutra vacía de contenedor; no inventa hechos ni cierra las posibilidades: conserva el booleano explícito de exhaustividad. La pregunta no recibe fuentes: sujeto/condiciones, solicitudes de propiedad/cantidad/procedimiento y premisas corregibles se extraen por separado. Las solicitudes conservan extensión inespecífica, máxima, total o común por separado. Cada cita se copia literalmente; procedencia textual no prueba significado, completitud o referencia.

## Prueba y puertas

Se implementan primero comprobaciones puras de negación, dato cero, clase/componente, identidad/collision, cantidad total/cota/ensayo, método ausente, planes/ejecución, capacidad/uso, disponibilidad acotada, varias cláusulas y lecturas abiertas. Ningún resultado manual equivale a extracción automática. El esquema compacto usa definiciones compartidas para explicar tipos; JSON object no garantiza esos tipos, que se verifican localmente sin reparar salidas.

Después, mismo piloto posicional de ocho operaciones: fuentes índices 0/27/55/82 y preguntas 0/10/21/32, sin etiquetas; GPT-4.1 Mini/OpenAI exclusivo, temperatura 0, máximo 4096 tokens, cuatro concurrentes, ocho HTTP y cero reintentos. Catálogo y estimación actuales se anuncian antes de red. Cada fuente recibe solo su texto/ontología y contrato compacto; cada pregunta, únicamente su texto/ontología y contrato. No se envían ejemplos de casos, resultados, frames, etiquetas ni catálogo de entidades. Preparación, source archive, diario y recibos nuevos.

Exigir 8/8 DTO completos y 8/8 fieles con dos críticas de todos los contenidos, sin gold ni roles esperados; declarar contexto previo de revisores si lo hubiera. Cada incertidumbre/defecto/ausencia bloquea el pase. Retener todas las operaciones, críticas y discrepancias. No se reemplaza la fuente por su etiqueta, se descartan cláusulas difíciles ni se cambia gold para pasar.

El piloto no prueba calidad poblacional, recursos ni integración. Aun si pasa: banco completo conocido, 126 difíciles, contraste contra baseline, recursos y estabilidad antes de abrir V6 nueva. Esta versión no cambia producto, SQL, secretos, dashboard o servicios. Reutiliza serde ya fijado en el workspace como dependencia directa de evaluación; no añade paquetes externos ni versiones (decisión 0023). Coste por recibo una vez; importe ausente desconocido. Tiempos de petición/runner separados de recall y latencia integrada.
