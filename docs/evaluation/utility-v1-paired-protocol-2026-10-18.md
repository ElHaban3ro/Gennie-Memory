# Protocolo previo: selección por utilidad v1

Fecha: 2026-10-18. Fijado antes de ejecutar la campaña remota. Hipótesis: la política base exige una respuesta específica y omite parte de la evidencia útil de refutación o contexto parcial. `utility_v1` admite explícitamente esas relaciones sin aceptar coincidencia temática sola. Cambian únicamente la instrucción y la descripción de la opción `none`; las demás opciones, pregunta, proveedor, búsqueda, condiciones y composición se conservan. No se incorpora segunda llamada ni inferencia de hechos faltantes. El texto exacto está en `UTILITY_V1_INSTRUCTIONS` y `UTILITY_V1_NONE`, congelado por hash del código y copia antes de ejecutar.

Banco: los 64 casos conocidos de `conversation-evidence-v1`, ocho conversaciones de desarrollo. Las etiquetas y rúbrica fueron fijadas antes de su línea base del 2026-10-17; esa línea base ya fue observada y motivó esta hipótesis. No es cohorte ciega, reserva ni revisión semántica independiente. Las frases y resúmenes coinciden; cada lista tiene ocho candidatos, sin prueba de truncamiento o compresión.

Se derivan dos casos por pregunta mediante `prepare-utility-comparison`, preservando todas las etiquetas. `baseline` y `utility_v1` se ejecutan adyacentes, alternando cuál va primero según la posición original, sin consultar etiquetas para ordenar. Un único proceso `session` y SQLite temporal comparten corpus; Decisions, `keywords`, límite 20, `campaign ... 128 per_case`. `per_case` es solo una opción del evaluador, no una política del producto. El runner valida cada política antes de iniciar, toma únicamente `request.search` y `request.selection_policy`, y no transmite relación, citas, justificación o IDs esperados al proveedor. No hay feedback de dashboard en la sesión directa.

Máximo: 128 operaciones, sin reintentos automáticos inciertos ni repeticiones para rescatar resultados. Duración prevista: 1–2 minutos; registrar tokens y coste reportados, y distinguir recibos ausentes de coste cero. Se ejecuta una sola variante, sin ajustar después de observar la campaña. La autorización vigente de investigación sintética permite esta comparación y exige dejar trazabilidad del gasto.

Criterios anteriores a la ejecución: bloquear si la variante pierde cualquier evidencia útil seleccionada por la base del mismo par, si selecciona un ID no permitido (incluida cualquier selección en ausencia) o si introduce degradación nueva. Para pasar a otra validación debe además recuperar al menos una evidencia útil que la base emparejada omita. No se compensa una regresión con ganancias en otra pregunta. Las doce omisiones históricas no son la referencia del filtro: se usa la base nueva del mismo par y se publican sus diferencias con la base histórica.

Se exige auditoría `audit-m5` de hashes, eventos, texto, fuente declarada, ámbito, revisión, estado y vigencia de candidatos y semillas antes de interpretar. El reporte debe rechazar listas de candidatos diferentes entre políticas. Se publican las cuatro relaciones separadas, transiciones pareadas, coste/tokens/recibos por política, versión del modelo y distribución de tiempos y diferencias por par; los tiempos no prueban aceleración poblacional. No se evalúa la verdad de una respuesta final generada.

Pasar este filtro de desarrollo solo permite proponer validación nueva. No cambia `baseline`, el límite 20, el README, el cierre limitado de M5 ni aprueba integración automática. Una corrección semántica posterior conservará etiquetas y resultados originales y quedará fuera del resultado prospectivo. Si falla, se registra y no se encadena otra variante en esta campaña.
