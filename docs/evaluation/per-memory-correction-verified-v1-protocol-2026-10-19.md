# Verificación selectiva de correcciones v1

Protocolo previo a llamadas. La repetición A/A de scopedV1 encontró un ID de otro libreto en una propuesta corrección=true/dato=false. Se conserva el resultado: una ejecución verde no probó estabilidad. Esta variante optativa `per_memory_correction_verified_v1` usa Jev1.13 para las dos preguntas originales scopedV1 sobre siete candidatos; el prefijo7 tiene cobertura retrospectiva suficiente para los IDs seleccionados anteriormente en V5, no garantía prospectiva. No modifica proveedor, ruta o política predeterminados.

Retrieval conserva cada dato solicitado con contexto=true, aunque la propuesta también diga corrección=true. Solo corrección=true/dato=false requiere un segundo juicio de Decisions. Cada juicio recibe exclusivamente consulta y un resumen literal, con una pregunta sobre corrección explícita del mismo referente/contexto; no comparte otros candidatos ni los juicios del proponente. Se rechazan asociación, hechos de otro objeto, planes, requisitos y silencio. La aceptación conjunta sigue siendo falible; no equivale a verdad ni revisión humana. No se extrae automáticamente una identidad certificada.

Bootstrap ejecuta una propuesta más cero a siete comprobaciones aisladas concurrentes. La traza `verification.scoped_proposal` conserva ambos juicios originales por ID/revisión; `proposal` conserva OR original y `checks` contiene exactamente las correcciones sin dato, en orden. Retrieval revalida cobertura/composición/consumo, y el evaluador audita el JSON de forma independiente. Un fallo de propuesta o comprobación degrada toda la operación y conserva todos los recibos conocidos una sola vez. Un recibo ausente no es coste cero ni total completo. La búsqueda vacía hace cero HTTP. No añade SQL, secretos, dependencias, puertos o servicios.

Piloto conocido de doce operaciones, una por pregunta, sin reintentos: los diez IDs de policy_probe más cev5q_068_03 (otro libreto) y cev5q_069_05 (contexto futuro permitido por gold original). Fuentes/gold V5 intactos. Contraste histórico contra Decisions/base y preservación adicional de todos los IDs útiles de scopedV1, sin llamar a ese contraste latencia emparejada. Máximo96HTTP (12 propuestas+84 comprobaciones); estimación USD0,003 y duración1–2minutos. Es una campaña CLI breve, sin puerto, con DB temporal propia. Binarios, archivos y protocolo congelados antes de gastar. Primeras dos operaciones validan transporte/traza; si son completas se ejecutan las diez restantes en el mismo diario, una sola vez.

Cero ID ajeno, pérdida de evidencia útil de base o scopedV1 y degradación. Recibos completos y coste histórico del subconjunto<=1,5× para permitir expansión; la latencia histórica se muestra solo como diagnóstico. Debe existir evidencia de mejora (ID útil ganado o ajeno eliminado en comparación documentada), sin compensar pérdidas con ganancias. No retirar del gold el contexto discutido06912. Si falla, detener esta versión y explicar la causa, sin buscar una repetición afortunada.

Solo si pasa: comparación completa V5/64preguntas/128operaciones emparejada contra Decisions/base, preservación de scopedV1, controles conocidos V4/V2 y repetición fija de consistencia. Puertas vigentes: cero ID ajeno/pérdida de evidencia útil o partes disponibles/degradación nueva, ganancia real y coste/p50/p95<=1,5× con recibos completos. Solo después abrir V6 congelada, con revisión separada previa; nunca ajustar sobre V6. Ninguna aprobación del piloto significa adopción, generalización o integración final.
