# Verificación proporcional

Propietarios: pruebas junto a `apps/retrieval/src/`, fixtures sintéticos en `tests/fixtures/`, comandos Cargo desde la raíz. Los ejemplos sintéticos no contienen recuerdos reales. La suite actual verifica ámbito, revisión, entrada FTS, vectores/cobertura y rechazo de elecciones no presentadas al clasificador. Los pilotos acotados verifican clasificación integrada con FTS5 o híbrido y semilla, sin probar el conjunto completo de métodos, permisos de un host, latencia del hook ni despliegue.

Para cambios de búsqueda o SQL: `cargo test --offline -p iromem-retrieval`. Para cambios de contratos, kernel, migraciones, registro o Cargo: `cargo test --offline --workspace`. Antes de entregar: `cargo fmt --all --check`. Una comprobación CLI breve usa una DB temporal: carga `tests/fixtures/small-corpus.json` y consulta `tests/fixtures/small-query.json` con `IROMEM_DATABASE_PATH` apuntando a esa DB; limpia solo los archivos que creó la prueba. No ejecutes dos Cargo a la vez sobre el mismo target.

Las pruebas significativas cubren comportamiento observable y fallos, no repiten simplemente la implementación. Al añadir proveedores, separa unitarias deterministas, integración local de Laya y llamadas remotas. El benchmark grande requiere definir corpus y duración prevista, además de presupuesto o autorización expresa para ejecutarlo sin tope monetario; no lo añadas a hooks ni CI obligatoria. La autorización vigente para esta investigación sintética permite ejecutarla sin tope monetario y exige registrar el coste informado o reservado. Registra qué se probó en el código actual y qué solo se revisó estáticamente. Una prueba pasada en un commit anterior o el verificador SQL adjunto al README no prueba la implementación presente.

Banco actual: `python3 scripts/validate_benchmark.py tests/benchmark/v1` y el mismo comando con `v2`–`v5` comprueban las cinco suites versionadas; `search-batch` permite una corrida CLI con conexión compartida y DB temporal. `cargo test --offline -p iromem-retrieval` incluye ámbito, revisión, vector inválido, cobertura parcial, revisión antigua, condiciones/fuente declarada y candidatos presentados. `python3 -m unittest discover -s tests -p 'test_*.py'` verifica contratos de los scripts Python. Los pilotos de Laya y OpenRouter son voluntarios y están documentados en [contract-v1.md](../evaluation/contract-v1.md). El [banco de recuerdos generales](../evaluation/general-memory-v1-results.md) usa sujetos disjuntos de desarrollo y final; sus vectores, base y diarios de proveedor quedan fuera de CI en `.local/pilots/`. No ejecutes la partición final al ajustar instrucciones o umbrales; una muestra de desarrollo no establece superioridad de modelo.

El [seguimiento v2](../evaluation/general-memory-v2-results.md) usa sujetos 006–009 de la reserva para una comprobación posterior; estos sujetos tampoco se reutilizan para ajustar prompts o umbrales. Las campañas nuevas solo clasifican con Decisions y Jev; Laya sigue como codificador experimental de vectores. Conserva sujetos posteriores al 009 para validación futura.

La [comparación de la consulta rápida](../evaluation/keyword-preflight-v1.md) mide el binario anterior y el nuevo con la misma base y las preguntas generales ya congeladas. `query_mode: "keywords"` es optativo; no se promueve una regla de salto semántico por una mejora de p50 si disminuye la cobertura. La prueba de seis casos con Decisions y la simulación de Codex tienen alcances distintos y se informan por separado.
