# SQLite y migraciones

Propietarios: `kernel/src/db.rs`, `apps/retrieval/migrations/` y `apps/retrieval/src/repo.rs`. El proceso CLI abre una conexión a la ruta explícita `IROMEM_DATABASE_PATH` y la entrega a la app; cada conexión habilita `foreign_keys` y `busy_timeout`. No uses la base de desarrollo para pruebas automatizadas: las unitarias abren SQLite en memoria y la prueba CLI usa una ruta temporal propia.

Cada app posee sus tablas y proyecciones. `dashboard` posee `dashboard_reviews`, registro append-only de revisión con instantánea de candidatos y decisiones; usa la misma conexión SQLite que retrieval. La primera migración posee `memories`, `memory_revisions`, `search_documents` y `memory_fts`; la segunda añade `embedding_spaces` y `memory_embeddings`; la tercera añade `entity_id` e índice por ámbito/entidad; la cuarta añade condiciones y fuente declarada a cada revisión sin reescribir migraciones anteriores. Es un esquema experimental, no el `schema-v1.sql` completo del README. Las revisiones conservan historial y solo `current_revision` entra en búsquedas actuales. Los triggers mantienen FTS en la misma transacción que la proyección. Filtra ámbito, entidad cuando se aporta, revisión, estado y tiempo antes de `LIMIT`; una coincidencia textual o semántica no amplía permisos. `space_id` no puede cambiar de modelo, tokenizer, procedimiento o dimensión, y un vector de revisión antigua no se usa para la revisión vigente.

`schema_migrations` registra versión y SHA-256 por módulo. Nunca edites bytes de una migración aplicada: añade una nueva. El registro de bootstrap ordena módulos antes de migrar y cada módulo entrega versiones crecientes. Una carga de fixtures o vectores es una transacción completa; no hagas inferencia de modelos dentro de ella. Las identidades sintéticas de un fixture no pueden cambiar de ámbito ni entidad. La auditoría general de acciones reales, rollback entre binarios y borrado físico se diseñarán cuando entren esas capacidades; no afirmes garantías que este esquema no implementa.

Verifica cambios SQL con `cargo test --offline -p iromem-retrieval` y una base SQLite nueva. Si cambia kernel/db o una migración, ejecuta `cargo test --offline --workspace` y comprueba el rechazo de checksum. Al ampliar hacia embeddings, conserva `(memory_id, revision, space_id)` y no mezcles espacios ni vectores antiguos con la revisión actual.
