# Configuración y secretos

## Contrato de producto v1 (2026-10-23)

recall-v1 usa la configuración/credencial existente y presupuestos explícitos por solicitud. segment-text y provider-capabilities no requieren configuración ni base. No añadir tokens/precios supuestos a los presupuestos de bytes. [Contrato y límites](../architecture/product-contract-v1.md).

Propietarios: `kernel/src/config.rs`, `bootstrap/src/main.rs`, `.env.example` y `.env` local ignorado. La única variable obligatoria sigue siendo `GENNIE_MEMORY_DATABASE_PATH`; no hay default implícito en código. El `.env` local conserva `.local/iromem.db` para acceder a los datos existentes, fuera de Git; `.env.example` propone `.local/gennie-memory.db` para instalaciones nuevas. Las variables ya exportadas tienen precedencia sobre `.env`. La app puede arrancar con solo entorno, sin archivo. El dashboard fue retirado; no hay puerto de servidor ni parámetros de UI.

`Config` contiene rutas no secretas; `Secrets`, sin `Debug`, lee opcionalmente `GENNIE_MEMORY_OPENROUTER_API_KEY`. No almacenes tokens en `Config`, en `AppState`, logs, errores, fixtures o `.creation/`. La variable de clave está comentada en `.env.example` sin valor real. El adaptador Rust de OpenRouter sirve `recall` y `session`; `gennie-memory-eval` invoca esa misma ruta para campañas sintéticas. `GENNIE_MEMORY_EVALUATION_CAPTURE_PATH` es una opción temporal de evaluación: si se define, apunta a un archivo JSONL nuevo y registra hashes SHA-256 del cuerpo de solicitud, prompt, esquema y respuesta completa, junto con ámbito, modelo, versión HTTP, latencia y recibo comunicado; nunca guarda el contenido ni la clave. `GENNIE_MEMORY_EVALUATION_RESPONSE_CONTENT_PATH` es una segunda opción independiente y opt-in que conserva solo el campo `choices[0].message.content` completo cuando no supera el límite local de traza; se usa exclusivamente con entradas sintéticas porque ese texto puede contener datos de entrada. El JSONL registra también el hash del cuerpo de solicitud para emparejarlo con la captura de metadatos. Mantén el archivo nuevo, local y con permisos restrictivos; no se sobrescribe. No habilites esta opción en uso normal ni en datos reales. Si ambas opciones se omiten, no hay captura ni cambio de comportamiento. Para proveedores nuevos, usa nombres `GENNIE_MEMORY_*`; documenta los placeholders sin credenciales. Valida ausencia, vacío, rango y combinación antes de abrir recursos; no elijas una base distinta al faltar la ruta. Las variables ya exportadas prevalecen sobre `.env`; si incorporas un aviso de discrepancia, informa solo el nombre, nunca el valor.

Los [perfiles de campaña v1 y v2](../../config/classifier-profile-v2.json) se conservan como metadatos de resultados históricos; el runner Python que los leía fue retirado. La CLI Rust `recall` fija la política vigente mediante sus valores por defecto y los campos de cada consulta: `provider` opcional elige Decisions o Jev, `search.query_mode` elige el modo FTS5 y `selection_policy` omitida usa `baseline`. `epistemic_partial_single_pass_v1` permanece disponible como opción experimental explícita; la restauración se registra en la [decisión 0044](../decisions/0044-restore-baseline-default.md). Las opciones explícitas `evidence_v1`, `support_gate_v1`, `utility_v1`, `utility_v2` y `witness_v1` no añaden variables de entorno. El evaluador Rust invoca la misma CLI, sin leer esos perfiles. `GENNIE_MEMORY_OPENROUTER_API_KEY` se lee del entorno o `.env` al invocar `recall`, nunca de su JSON; una búsqueda vacía no requiere petición remota. El perfil local de embeddings v1 ya fija identidad, revisión, hashes, tokenizer, runtime y límites en settings explícitos (ver contrato local-embeddings); la configuración editable general del producto sigue pendiente: distingue configuración de proceso de ajustes editables por app. Toda notificación de cambios persistidos se envía después del commit. Una nueva variable exige actualizar lector, ejemplo, docs y una prueba de configuración en el mismo cambio.

Comprobación actual: `GENNIE_MEMORY_DATABASE_PATH=/ruta/temporal.db cargo run --offline -p gennie-memory -- init-db`. Usa una ruta de prueba, no la base del usuario. El error por variable faltante se comprueba con entorno controlado; no borres `.env` ajeno para hacerlo.

En `witness_v1`, el extractor está fijado experimentalmente a `openai/gpt-4.1-mini` en el adaptador, con el mismo secreto de OpenRouter, salida JSON Schema y sin fallback. No añade variables ni configuración editable del usuario. Su consumo se registra aparte del proponente y agregado cuando ambos recibos se conocen.

`roles_v1` añade otra política explícita experimental sin variables ni modelos nuevos. Cambia instrucción y opción `none` dentro de la elección existente; no cambia configuración predeterminada.

`roles_fallback_v1` es otra política experimental explícita, sin variables nuevas: base y, solo tras abstención, selección por roles del mismo proveedor. No tiene extractor ni mezcla probabilidades.

`roles_v2` es optativa experimental y fallida en desarrollo. El perfil de evaluación `jev_roles_v1` usa los campos existentes `provider: jev`, `selection_policy: roles_v1`; no es otro enum runtime ni cambia secretos/modelos predeterminados.

Las políticas optativas `roles_consensus_v1` y `roles_consensus_batch_v1` no cambian proveedor implícitamente; los perfiles `jev_roles_consensus_v1`/`jev_roles_consensus_batch_v1` del evaluador fijan `provider: jev`. Clasifican hasta16 de20 recuperados. La variante paralela hace dos peticiones y suma recibos; por lote hace una y no duplica el global. No añaden configuración/secretos.

`roles_consensus_shared_v1` conserva veinte candidatos en un mapa `state.memories` escrito una sola vez y hace dos preguntas con referencias a ese mapa en una petición. Mantiene traza y recibo global único; a diferencia de los consensos previos no recorta a dieciséis. El servicio aplica el límite correspondiente a cada versión, sin alterar versiones anteriores. Perfil de evaluación `jev_roles_consensus_shared_v1` selecciona Jev explícitamente; no cambia el predeterminado. Su calidad requiere contraste, no se presume por el formato.

`roles_consensus_compact_v1` es optativa y clasifica los primeros4 de20 recuperados mediante las dos instrucciones congeladas y llamadas paralelas del consenso anterior. `SelectionPolicy::consensus_candidate_limit()` centraliza los límites por versión para adaptador y revalidación del servicio. El perfil de evaluación `jev_roles_consensus_compact_v1` fija Jev y reporta límite4; comprobar cobertura útil y mejor relación antes de medir, IDs fuera del cuarto puesto y puertas de calidad/recursos intactas. [Protocolo](../evaluation/roles-consensus-compact-v1-protocol-2026-10-19.md).

`roles_consensus_mirrored_v1` conserva top16 y dos preguntas por petición con las instrucciones congeladas. El segundo voto usa esos mismos recuerdos en orden inverso y se remapea a ID antes de comprobar acuerdo. `consensus.votes` contiene IDs normalizados; el recibo global se cuenta una vez. Es optativa, con límite16 revalidado por servicio y perfil Jev explícito `jev_roles_consensus_mirrored_v1`; no cambia proveedor o selección predeterminados. Pruebas cubren etiqueta igual/ID distinto, etiqueta distinta/ID igual y listas menores al límite. [Protocolo](../evaluation/roles-consensus-mirrored-v1-protocol-2026-10-19.md).

`roles_primary_veto_v1` es agregación asimétrica optativa de las mismas dos preguntas/orden de mirrored: conserva el primer ID ante acuerdo o abstención del segundo; rechaza un segundo ID distinto y no rescata propuestas ausentes. No es verificación independiente ni acuerdo exacto. La traza heredada `consensus` contiene votos normalizados; `SelectionPolicy::resolve_votes()` define la regla que revalida el servicio. El evaluador verifica esa política y desglosa aceptación sin segundo voto. Votos inválidos/ausentes degradan con recibo global único. Perfil Jev explícito, sin cambiar defaults. [Protocolo](../evaluation/roles-primary-veto-v1-protocol-2026-10-19.md).

`per_memory_v1` es una variante optativa con un juicio por cada top16recuerdo en una petición; conserva todos los positivos en una semilla múltiple. `retrieval::per_memory` posee tipos/validación y `bootstrap::openrouter::per_memory` el protocolo. `selected_ids` enumera toda semilla; el alias singular no basta para auditarla. No añade tablas, conexiones, dependencias, variables ni servicios. Pruebas verifican conjunto completo, revisión, fallo atómico y recibo global único; calidad y tamaño/coste de contexto requieren medición. [Contrato](../evaluation/per-memory-v1-contract.md).

`per_memory_v2` es la variante experimental explícita de ocho candidatos del contrato por recuerdo; v1 conserva dieciséis. Ambas componen todos los positivos, validan el conjunto completo y mantienen un único recibo por petición. El compositor público conserva el máximo histórico de ocho; solo la ruta automática v1 permite dieciséis. Protocolo: [per-memory-v2](../evaluation/per-memory-v2-protocol-2026-10-19.md).

Variantes posteriores optativas: `per_memory_v3` conserva ocho candidatos e incluye la consulta en cada pregunta; `per_memory_v4` conserva ocho y utiliza payload compacto con Decisions en su protocolo. Cambian texto/modelo, no el valor predeterminado ni las puertas. V3 falló diagnóstico conocido y no se amplió. Protocolos versionados en `docs/evaluation/per-memory-v{3,4}-protocol-2026-10-19.md`. El evaluador rechaza opciones globales de campaña que contradigan proveedor o política declarados por caso antes de llamar al proveedor.

`per_memory_binary_v1` ensaya utilidad binaria optativa sobre8candidatos; traza positiva `useful_evidence` no atribuye relación semántica. El servicio rechaza mezcla con categorías de las variantes anteriores, conserva todos los positivos y un recibo global por petición. Comparte state/instructions con V2, cambia solo categorías. El diagnóstico factorial conocido en `tools/evaluation/src/per_memory_matrix.rs` compara tareas, contextos y proveedores, audita semilla completa y no es puerta de promoción. [Protocolo](../evaluation/per-memory-binary-v1-protocol-2026-10-19.md).

`per_memory_verified_v1` es una política experimental optativa: Jev propone utilidad binaria sobre ocho candidatos y Decisions verifica cada positivo en una petición aislada (máximo nueve HTTP, verificaciones concurrentes). Retrieval revalida intersección, IDs/revisiones y recibos; bootstrap posee transporte. Un fallo degrada toda la operación; recibos faltantes impiden presentar subtotales como total. No cambia defaults, secretos, SQL ni dependencias. `validate-verified-pilot` vincula los diez casos conocidos con sus originales antes de llamar; `report-verified-pilot` exige auditoría vigente y desglosa toda semilla, evidencia de base perdida, modelos y consumo por etapa. La búsqueda vacía exige cero llamadas. [Contrato y puertas](../evaluation/per-memory-verified-v1-contract.md).

`per_memory_binary_v2` ensaya utilidad estricta y compacta en una sola petición Jev sobre8recuerdos, sin verificador: dato solicitado o negación explícita de premisa, nunca inferencia por silencio o requisito asociado. Composición/recibos y puertas intactos; variante anterior conservada. Los comandos de piloto admiten esta política y verifican diez casos originales congelados. [Protocolo](../evaluation/per-memory-binary-v2-protocol-2026-10-19.md).

`per_memory_binary_v3` conserva payload V2 salvo instructions de cada pregunta: acción explícita de evaluar el resumen respecto de la consulta, con el resumen literal como dato. Misma tarea binaria, prefijo8, un HTTP y recibo global único; no cambian defaults o recursos compartidos. Piloto18conocidas con todas las pérdidas y negativos previos; pasa a banco completo solo si conserva evidencia y precisión. [Protocolo](../evaluation/per-memory-binary-v3-protocol-2026-10-19.md).

`per_memory_binary_v4` deriva V3 añadiendo solo la prueba de incompatibilidad para refutar una premisa; después comprueba por separado hechos/partes solicitados. No exige contradicción para aceptar apoyo. Misma semilla múltiple/prefijo8/recibo único, sin cambiar defaults o recursos. Piloto34conocidas añade las16unrelated y conserva todas las puertas. [Protocolo](../evaluation/per-memory-binary-v4-protocol-2026-10-19.md).

`per_memory_binary_v5` conserva V3 y añade la prueba de incompatibilidad solo para correcciones, con OR explícito: dato/parte solicitados o corrección válida; none solo si ambos fallan. Corrige una ambigüedad detectada por revisión enV4, detenida tras1operación y conservada. Mismo límite/recibo/puertas; [protocolo](../evaluation/per-memory-binary-v5-protocol-2026-10-19.md).

`per_memory_scored_v1` instrumenta el payload/elección V5 sin alterar selección: choice_scores A/none y huella SHA-256 del payload por operación, con recibo global único. Retrieval valida cardinalidad/IDs/revisiones/scores; bootstrap captura valores y kernel expone SHA-256 con la dependencia existente. Evaluación prepara64conocidasv5 y analiza banda global con margen0,05 y punto medio predefinidos; no es confianza factual ni promoción. Sin nuevos secretos, tablas, índices, dependencias o puertos. [Protocolo](../evaluation/per-memory-score-diagnostic-protocol-2026-10-19.md).

`provider: "jev114"` selecciona experimentalmente `typesafe/jev-1.14` sin cambiar `jev` (1.13) ni Decisions predeterminado. Comparte el adaptador existente y no añade secretos/configuración de entorno. El runner admite ese proveedor explícito y rechaza contradicciones con el caso. La prueba compara payloads completos y exige que solo cambie `model`; el diagnóstico de20operaciones es conocido, no pase de desarrollo. [Protocolo](../evaluation/jev-version-probe-protocol-2026-10-19.md).

`per_memory_examples_v1` es optativa: deriva de binaryV5/Jev1.13 con seis demostraciones contrastivas en state, conserva prefijo8, tarea binaria y un recibo global. No cambia defaults ni env. Prueba de payload compara campos ajenos a ejemplos/reglas y prueba de servicio verifica toda la semilla. El piloto `report-policy-probe` liga20operaciones y fuente/gold previo, compara sets de IDs y no compensa pérdidas con ganancias. La auditoría ordinaria y recibos siguen obligatorios. [Protocolo](../evaluation/per-memory-examples-v1-protocol-2026-10-19.md).

`per_memory_factors_v1` es optativa: Jev1.13 responde tres choices independientes por cada top8en un HTTP y recibo único. Retrieval posee `MemoryFactorChecks` y composición contexto&&(dato||corrección), revalidada antes de semilla. La traza `factor_checks` es obligatoria solo en esta política; los booleanos son juicios fallables, no prueba semántica. Parser y auditor JSON independientes rechazan omisiones/IDs/revisiones/agregación alterada. `report-factor-probe` usa el piloto fijo20operaciones; ausencia de recibos bloquea recursos. Sin nuevos env, tablas, dependencias o puertos. [Contrato y protocolo](../evaluation/per-memory-factors-v1-protocol-2026-10-19.md).

`per_memory_scoped_v1` es optativa: dos choices por cada top8en un HTTP, para dato solicitado y corrección, cada vía requiere el mismo referente/contexto. Retrieval posee `ScopedEvidenceChecks` y OR local; no fabrica un tercer juicio de identidad. La traza `scoped_checks` pertenece a las variantes scopedV1/V2/V3, revalidada por servicio y auditor JSON. Parser conserva recibo global una vez, fallo atómico y búsqueda vacía sin llamada. `report-scoped-probe` usa veinte operaciones conocidas y puertas intactas. Sin nuevos env, SQL o dependencias. [Protocolo](../evaluation/per-memory-scoped-v1-protocol-2026-10-19.md).

`per_memory_scoped_v2` comparte tipos/parser/revalidación conV1; solo acorta descripciones de A/none, conservando preguntas, reglas, candidatos y modelo del contraste. Prueba de igualdad del resto del payload y medición real de coste/calidad obligatorias. `report-scoped-v2-probe` contrasta20operaciones contraV1con objetivo de coste estrictamente menor y calidad preservada. La campaña completa mantiene la puerta global contra Decisions/base y exige además conservar los IDs útiles deV1. [Protocolo](../evaluation/per-memory-scoped-v2-protocol-2026-10-19.md).

`per_memory_scoped_v3` preserva instrucciones/reglas/criteriosV1y solo aplana/acorta alias técnicos de memorias/preguntas. Parser remapea nombres de respuestas, sin fabricar elecciones ni probabilidades. Prueba de reversión del esquema exige payload original idéntico; la calidad/coste del modelo se miden aparte. `report-scoped-v3-probe` exige menor coste y calidad preservada contraV1, antes de puerta global y preservación completa de sus IDs útiles. [Protocolo](../evaluation/per-memory-scoped-v3-protocol-2026-10-19.md).

`per_memory_complete_premise_v1` añade solo una política explícita experimental: el proveedor de propuesta sigue siendo el campo existente (perfil evaluado Jev), y el verificador de esta política es Perplexity Decider V1.2 con revisión servida obligatoria. No es un nuevo proveedor de propuesta ni fallback implícito, variable o secreto. Usa la clave OpenRouter existente. Omitir política conserva baseline.

`per_memory_scoped_anchor_v1` usa el proveedor explícito existente y siete candidatos; no añade credenciales, variables ni fallback remoto. Omitir política conserva baseline. La traza diferencia nombre ausente de presencia literal falsa mediante `Option`. [Protocolo](../evaluation/scoped-anchor-v1-protocol-2026-10-19.md).

La feature de compilación optativa `gennie-memory/http2-transport` habilita soporteHTTP/2sin variables ni credenciales nuevas. No es configuración runtime ni habilita otra política. Omitirla conserva la build/transporte anterior. Su pase de recursos requiere negociación observada, no basta con compilar. [Decisión0022](../decisions/0022-opt-in-http2-evaluation.md).

`provider: "gemma3_4b"` es un proveedor experimental explícito (`google/gemma-3-4b-it`) que usa chat completions para `baseline`, `slot_evidence_v1` y `slot_evidence_v2`; no cambia Decisions predeterminado ni habilita otras políticas. Reutiliza la credencial OpenRouter existente. V1 falló su gate estructural de smoke; V2 es candidata separada aún sin smoke puntuable. Ninguna certifica semántica ni autoriza promoción.

La ruta `embedding-session <settings.json>` requiere compilación con `local-embeddings` y la DB configurada existente. `config/embedding-profiles/e5-small.json` es el perfil seleccionado; MiniLM conserva el control comparativo. `artifact_dir` es una ruta local explícita, resuelta desde el cwd; no forma parte del espacio semántico ni se descarga por defecto. No se añade variable obligatoria o secreto. `RAYON_NUM_THREADS=4` y `TOKENIZERS_PARALLELISM=false` son condiciones de las mediciones, no requisitos de autenticación/configuración persistida. [Contrato](../architecture/local-embeddings.md).

## Tokens por petición de producto (2026-10-24)

`ProductRequest.budgets.input_tokens` (16384) y `seed_tokens` (2048) son límites locales de referencia `o200k_base`, rango 1–65536. No hay variable de entorno ni autodetección de tokenizer del proveedor; bytes/plazo se validan por separado. No se interpretan como contexto nativo, precio o recibo. [Contrato](../architecture/product-contract-v1.md).

## Fuentes locales por operación (2026-10-24)

Source_policy en recall-v1: report por defecto, require_verified explícita; limita publicación de semilla, no autorización de red. Registro/comprobación usan actor_id local por defecto y scope exacto. Registro aporta texto UTF-8 hasta 256 KiB y versión inmutable; ref no se interpreta como ruta o URL. Locator utf8:start:end usa bytes/final exclusivo. Sin nueva variable, secreto, dependencia o configuración de conector. [Contrato](../architecture/product-contract-v1.md).

## Extensión de recall (2026-10-24)

Recall-v1 acepta artefacto calibration inline optativo, ligado a proveedor/política/modelo/huella exacta; no añade entorno o secreto. Source-import-https acepta URL y SHA256 esperado explícitos, no usa proxies de entorno ni credencial OpenRouter. HTTPS normal valida certificados; no deshabilitar TLS ni seguir redirects. [Contrato](../architecture/recall-completion-v1.md).
